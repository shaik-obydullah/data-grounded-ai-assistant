1. Executive Summary

The Home Office publishes its Register of Licensed Sponsors as a monthly CSV release — a raw, 140,000+ row flat file with no search, no change tracking, and no user interface. This case study presents the design, development, and deployment of a UK Sponsor Directory that turns that static spreadsheet into a searchable, change-aware, AI-assisted business platform.

The system was built using Laravel 13 (PHP 8.5), containerised with Docker Compose, backed by PostgreSQL 16, and integrated with Ollama for a private, local AI assistant. It serves six distinct audiences: immigration & compliance teams, recruitment agencies, HR departments, business development teams, data analysts, and policy researchers.

The platform ingests large CSV exports with a live two-phase progress bar, automatically detects changes between monthly releases using per-row MD5 checksums, maintains editable contact records, and augments the experience with a data-grounded AI assistant — a conversational interface whose answers are anchored in live dataset statistics through context-augmented generation (CAG) rather than retrieval-augmented generation (RAG).

2. Problem Statement

2.1 Background

The Home Office updates its Register of Licensed Sponsors roughly once a month. While the data is public and authoritative, anyone who relies on it faces critical operational problems:

  • No Interface: A 140,000+ row flat CSV with no search, filtering, or browsing — unusable by non-technical staff
  • No Change Visibility: Monthly releases arrive silently; spotting which organisations were added, removed, or altered requires manually diffing enormous files
  • No Contact Data: The register contains no website, phone, or HR email, which users must otherwise maintain separately in spreadsheets
  • No Analytics: Questions such as “how many sponsors are in London?” or “which routes are most common?” require technical SQL skills
  • Manual, Error-Prone Workflows: Without automation, keeping track of changes month to month is impractical

4. System Design

4.1 Database Schema

The system uses 6 normalized tables with proper relationships:

Table Purpose
users Framework default users table
csv_imports Import records with filename, file MD5 checksum, total rows, per-category counts, JSON summary, status, and progress (0–100)
companies Sponsor records: organisation name, town/city, county, type & rating, route, editable contact fields, per-row MD5 checksum, import link, and change type
chat_messages Per-session AI conversation history (role, content, model)
cache / jobs Framework default cache and job queues

4.2 Entity Relationships

csv_imports -----< companies        // every company links to the import that produced it
companies  ------- csv_checksum       // per-row MD5 for change detection
chat_messages     session_id (index)  // cookie-scoped conversation history

4.3 Change Detection Logic

Each import computes a file-level checksum (md5_file) to find the previous comparable import, and a per-row checksum (md5(json)) for every record. Rows are then classified:

if row checksum exists in previous import      -> change_type = 'unchanged'
else if organisation name already exists       -> change_type = 'updated'
else                                           -> change_type = 'new'
Rows from the previous import missing now      -> deleted (change_type 'removed' via diff)

4.4 AI Context Injection

Rather than retrieval (RAG), the assistant uses context-augmented generation (CAG): every request builds a live summary — total company count, breakdowns by route and type/rating, recent change counts, and 3 sample records — and injects it into the model’s system prompt. Answers are therefore always grounded in real, current data with no retrieval index to drift out of sync.

7. Implementation Challenges & Overcomes

Challenge 1: Importing 140K+ Rows Efficiently

Problem: A single register release contains 140,000+ rows. Naively inserting one-by-one with Eloquent would exhaust memory and take minutes or hours.

Solution: Batched bulk inserts — 500 rows at a time with Company::insert(), committing to the database every 5,000 rows. Progress is written to the import record so the UI can poll it live.

$batchSize = 500;
if (count($toInsert) >= $batchSize) {
    Company::insert($toInsert);
    $toInsert = [];
}
if ($count % 5000 === 0) {
    DB::commit();
    DB::beginTransaction();
}

Result: Large exports (10.9M rows, 2GB) process with bounded memory and a smooth progress curve from 0 to 100%.

Challenge 2: Reliable Change Detection

Problem: Comparing two monthly releases to classify every row as new, updated, unchanged, or removed must be exact and fast — string comparison over 140K rows is neither.

Solution: Per-row MD5 checksums. The current file’s checksums are looked up against the previous import’s checksum set; rows missing from the current set are removed via a checksum diff.

$rowChecksum = md5(json_encode($row));
$currentChecksums[] = $rowChecksum;

if (isset($existingChecksums[$rowChecksum])) {
    // unchanged
} elseif (isset($existingNames[$row['organisation_name']])) {
    // updated
} else {
    // new
}
// removed = array_diff_key($existingChecksums, $currentChecksums)

Result: Exact, fast classification distinguishing content updates from genuine additions and removals.

Challenge 3: Real-Time Progress Feedback

Problem: Users needed to see progress for both the browser upload and the server-side processing of very large files.

Solution: A two-phase AJAX flow. Upload uses xhr.upload.onprogress for byte-level feedback; processing uses a second AJAX call that polls a /progress endpoint every 1.5 seconds reading the persisted progress field.

Result: Users see accurate, live progress through upload and row-by-row processing phases.

Challenge 4: Container Networking & Startup Order

Problem: Five containers (app, nginx, postgres, adminer, ollama) must coordinate on a shared network, and the app must wait for the database before migrating.

Solution: A bridge network with compose service names for internal hostnames, a PostgreSQL health check (pg_isready), and depends_on: condition: service_healthy. Host and database credentials are isolated from the public internet.

Result: One-command startup with correct service ordering; no “connection refused” races.

Challenge 5: Keeping AI Answers Accurate

Problem: Without grounding, a language model will invent statistics about the dataset. Retrieval (RAG) over 140K rows would require embeddings, a vector store, and constant re-indexing.

Solution: Context-augmented generation — inject a live aggregate summary (totals, route/rating breakdowns, recent change counts, sample records) into the system prompt on every request. The model answers from real, current data with no index to drift.

Result: Instant, deterministic, auditable answers — and no hallucinated statistics.

Challenge 6: Zero-Downtime Rebrand & Migration

Problem: During a full rebrand and rename of the application, all 143,313 records had to be preserved while the data layer and AI model store were relocated.

Solution: A pg_dump backup/restore carried over every record; the Ollama model store was migrated to the new Docker volume.

Result: 100% data preservation with no loss across the migration.

Challenge 7: Private, Self-Hosted AI

Problem: Sponsor data is commercially sensitive; sending it to a public AI API was unacceptable.

Solution: Ollama runs as a first-class container with the model persisted in a Docker volume. No external API keys and no data leaving the environment.

Result: Fully private AI processing viable for compliance-sensitive work.

11. Lessons Learned

11.1 Technical Lessons

  1. Batch Inserts Beat Per-Row ORM: Bulk inserting 500 rows and committing every 5,000 is the difference between a 2-hour import and one that streams to 100% with bounded memory.
  2. Checksums Make Diffs Exact: Per-row MD5 checksums turn a fragile string-comparison problem into an exact set operation.
  3. Grounding Beats Retrieval for Structured Data: For aggregate questions, injecting live statistics (CAG) is simpler, cheaper, and more accurate than a full RAG pipeline — and it can never go stale.
  4. Persist Progress to the Database: A single progress column read by a polling endpoint is a simple, reliable way to show long-running jobs to users.
  5. Health Checks Fix Startup Order: Using service_healthy conditions removes container orchestration races.

11.2 Process Lessons

  1. Design for Multi-Audience Use: The platform’s value multiplied when each persona (compliance, recruiting, sales, analytics) found its own workflow in the same tool.
  2. Normalise CSV Headers Defensively: Header variants (“Town/City” vs “Town City”, “Type & Rating” vs “Type Rating”) required a mapping layer to avoid silent data loss.
  3. Keep the Data Layer Portable: Using Docker volumes for both the database and the AI model store made the zero-downtime migration straightforward.

13. Conclusion

The UK Sponsor Directory demonstrates how modern web technologies can turn a raw public dataset into a genuinely useful business tool. By combining Laravel 13’s robust framework, PostgreSQL’s reliability, Docker’s containerisation, and Ollama’s private, data-grounded AI, the system delivers a fast, secure, and intelligent platform for managing the UK’s sponsor register.

The project’s success lies in its thoughtful architecture — batched imports for large-file performance, MD5 change detection for exact diffs, contact enrichment for actionable records, and context-augmented generation for answers that never hallucinate statistics. These design decisions made the system feature-complete, performant, and production-ready across six distinct audiences.
